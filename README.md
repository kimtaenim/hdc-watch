# hdc-watch

HDC(하이퍼디멘셔널 컴퓨팅) 학습 노트이자 실험 장치. 톱니바퀴가 다 보이는 투명 시계를 목표로 한다.

HDC 학습용 실험이며 투자 판단 자료가 아님.

각 설명 끝의 꼬리표는 그 문장이 무엇인지 밝힌다.
[수학] 수학적 사실(근사면 근사라고 적음) / [관찰] 이 저장소의 데이터나 테스트에서 실제로 본 것 / [비유] 이해를 돕는 비유 / [설계] 이 프로젝트가 고른 방식 / [사실] 수학 밖의 사실(시장 구조, 자료의 성격 등) / [추측] 확인하지 못한 짐작

## 한 줄 요약 (표준 용어)

바이너리 스패터 코드(Binary Spatter Code, Kanerva)로 요일, 시간대, 거래량 수준 벡터를 묶고(binding) 더해(bundling) 만든 프로토타입과 비교하는, 프로토타입 기반 이상탐지. 비교는 정수 프로토타입과의 코사인(정수 점수, 본 점수)과 이진 프로토타입과의 해밍 유사도(이진 점수, 바이너리 스패터 코드 본래 방식, 비교용) 둘 다 한다.

| 이 저장소의 말 | 표준 용어 |
| --- | --- |
| 이름별 기본 벡터 | item memory, codebook |
| 묶기 / 풀기 (XOR) | binding / unbinding |
| 더하기 | bundling, superposition |
| 정수 프로토타입 | 다수결 전 bundle (accumulator) |
| 이진 프로토타입 | 다수결로 만든 0/1 bundle (binarized prototype) |
| 수준 벡터 | level hypervectors |
| 잡음 | crosstalk |
| 가장 닮은 후보 고르기 | cleanup |
| 담을 수 있는 한계 | capacity |

## ① 공용 HDC 부품

### 톱니바퀴 1: 벡터 만들기 (`hdc/vectors.py` `make_vector`)
- 이름(예: `요일:수`) 뒤에 `#0`, `#1`, ...을 붙여 SHA-256 해시를 내고, 바이트마다 큰 자리 비트부터 이어 붙여 앞 10,000비트를 쓴다. 해시 40번이면 10,240비트가 나온다. [설계]
- 난수 생성기를 쓰지 않으므로 같은 이름은 어디서나 같은 벡터다. 벡터 파일을 저장하지 않는다. [설계]
- 무관한 300쌍의 유사도: 평균 +0.0004, 표준편차 0.0097, 가장 큰 절댓값 0.0292. 300쌍 모두 ±0.03 안. [관찰]
- 이론상 표준편차는 약 1/√D = 0.01이다(정규 근사). 칸마다 같을 확률 1/2인 동전 D개를 던진 것과 같아서다. 단, SHA-256 출력을 무작위로 볼 수 있다는 가정 위에서다. [수학]

### 톱니바퀴 2: 묶기 = XOR (`hdc/ops.py` `bind`)
- 같은 칸이면 0, 다르면 1. (A⊕B)⊕B = A이므로 풀기도 같은 XOR이다. [수학]
- A, B가 무관한 무작위 벡터면 묶은 결과는 A와도 B와도 무관하다(유사도 0 근처). "요일 × 시간대 × 단계"를 묶은 벡터는 셋 중 어느 것과도 닮지 않은 새 주소가 된다. [수학] 새 주소라는 표현은 [비유]

### 톱니바퀴 3: 비교 = 해밍 거리 (`hamming`, `similarity`)
- 해밍 거리 = XOR 후 1의 개수 = 서로 다른 칸 수. 유사도 = 1 - 2 × 거리 / D. [수학]
- word2vec의 코사인 유사도와 같은 역할이다. 0/1 벡터를 +1/-1로 바꾸면 이 유사도는 코사인 유사도와 정확히 같다. [수학]

### 톱니바퀴 4: 수준 벡터 (`level_vectors`)
- 1단계는 이름에서 꺼낸 벡터. 칸마다 `뒤집기|이름|칸번호`의 해시 앞 8바이트를 제비 번호로 주고 작은 순으로 줄 세운 뒤, 한 단계 오를 때마다 그 줄에서 다음 묶음을 뒤집는다. [설계]
- 12단계에서 단계마다 뒤집은 칸 수: 454, 455, 454, 455, 454, 455, 454, 455, 454, 455, 455 (합 5,000). [관찰]
- 뒤집은 칸이 겹치지 않으므로 두 단계 사이 거리는 그 사이 뒤집은 칸 수와 정확히 같다. 1단계와의 유사도: 1.000, 0.909, 0.818, 0.727, 0.636, 0.546, 0.455, 0.364, 0.273, 0.182, 0.091, 0.000. [수학, 테스트로 144쌍 모두 확인]

### 톱니바퀴 5: 더하기 = 프로토타입 (`Memory`)
- 칸마다 정수를 둔다(정수 프로토타입). 들어온 벡터의 칸이 1이면 +1, 0이면 -1. 다수결로 0/1을 정하면 이진 프로토타입이 된다. [설계]
- 짝수 개를 더하면 0:0으로 비긴 칸이 생긴다. 이 칸은 고정 벡터 `__동점깨기__`의 칸을 따른다. 그래야 파이썬과 브라우저가 같은 답을 낸다. [설계]
- 정수 프로토타입은 덧셈만으로 갱신되고 순서와 무관하다. [수학] 다만 모델에는 그 밖에도 중앙값, 단계 경계, 판정 기준이 있고, 이것들은 자료가 늘면 다시 계산한다. [설계]
- 동점깨기 벡터를 모든 프로토타입이 함께 쓰므로, 이진 프로토타입들이 이 벡터 쪽으로 조금 치우친다. 더한 수가 짝수면 동점 칸이 생긴다(620봉 전체: 70칸). [관찰]
- 35개 조합(요일 5 × 시간대 7, 단계는 임의 배정)을 프로토타입 하나에 더한 뒤 (요일 × 시간대)로 풀어 물으면 35개 모두 저장한 단계가 가장 가까웠다. [관찰]
- 세 조합만 더한 자체 점검에서 (수 × 14시대)로 풀어 묻자 9단계 0.507, 10단계 0.465, 8단계 0.462였다. 정답이 1등이지만 이웃 단계도 가깝다. 수준 벡터는 이웃끼리 닮게 만들었으니 당연한 결과이고, 답이 "한 점"이 아니라 "정답 근처에서 봉우리"로 나온다는 뜻이다. [관찰] 봉우리는 [비유]

### 파이썬과 브라우저의 일치
- `tests/test_hdc.py`가 node로 `docs/js/hdc.js`를 돌려, 한글·영문·이모지·빈 이름 벡터 8개, 수준 사다리 2개(D=10,000과 1,000), 동점 칸이 있는 프로토타입 1개의 비트가 파이썬과 한 비트도 다르지 않음을 확인한다. [관찰]
- 읽기용 기준 구현 `hdc/reference.py`(for문만 쓴 느린 판)와 numpy 판의 결과가 같음도 확인한다. [관찰]

### 추적 기록 형식 (`hdc/trace.py`)
실행 한 번이 JSON 하나를 남긴다. 화면은 이 파일만 읽어 그린다.

| 항목 | 담는 것 | 예 |
| --- | --- | --- |
| `steps[].op` | 쓰인 연산 | 벡터 생성 / 뒤집기 / 묶기 / 더하기 / 비교 / 일반 계산 |
| `steps[].why` | 설명과 그 성격 | `{"kind": "수학적 사실", "text": ...}` |
| `steps[].inputs`, `outputs` | 실제 값, 벡터 요약(1의 개수, 앞 64비트, 필요하면 1만 비트 전체) | `{"type": "vector", "ones": 5022, "head": "11000000...", "bits_b64": ...}` |
| `steps[].check` | 같은 질문을 단순 카운트로 푼 정답과 HDC 답 | `{"count_answer": 4954, "hdc_answer": 4954, "agree": true}` |
| `steps[].source` | 해당 코드의 파일과 줄 | `{"file": "hdc/ops.py", "line": 25, "function": "hamming"}` |
| `log` | 받은 건수, 실패, 메모 | |

예시: `python -m hdc.selfcheck`가 만든 `docs/data/traces/hdc/selfcheck.json`.

## ② 거래량: 60일 학습과 재채점

종목: 정원엔시스(045510.KQ). 결과는 `docs/data/volume/045510.KQ/`의 `model.json`(정수 프로토타입과 기준), `bars.json`(봉별 점수), `raw.json`(받은 원자료 그대로), `traces/`(추적 기록).

### 톱니바퀴 순서
| 단계 | 연산 | 하는 일 |
| --- | --- | --- |
| 원자료 받기 | 일반 계산 | yfinance로 5분봉을 받는다. 야후가 5분봉을 주는 최대 기간인 최근 60일이 학습 기간이다. |
| 하루 6개 봉 | 일반 계산 | 5분봉을 시간대별로 합쳐 9-14시대 봉을 만든다. 15시대(5분봉 없음, 역산 부정확)는 뺀다. |
| 중앙값 | 일반 계산 | 시간대마다 그 종목 자기 데이터의 중앙값. |
| 단계 나누기 | 일반 계산 | 중앙값의 몇 배인지를 2배 간격 12단계로. 6단계 = 1배-2배. |
| 벡터 꺼내기 | 벡터 생성, 뒤집기 | 요일 5개, 시간대 6개, 수준 벡터 12단계. |
| 묶기 | 묶기 | 봉 하나 = 요일 ⊕ 시간대 ⊕ 단계. |
| 프로토타입 | 더하기 | 모든 봉을 더한다. |
| 재채점 | 비교 | 봉 자신을 정수 프로토타입에서 뺀 뒤, 정수 점수(본)와 이진 점수(비교용)를 잰다. 낮을수록 드문 조합. |
| 판정 | 일반 계산 | 학습 점수 하위 1%를 이상, 5%를 주의 경계로. |

### 만들면서 확인된 것
- 지시서가 적은 중앙값 6개는 학습 창을 5/10-11/9로 잡았을 때 처음 받은 자료에서 정확히 재현됐다. 그러나 약 10분 뒤 다시 받은 자료에서는 9-11시대 중앙값이 달라졌다(9시대 9,397 → 9,862). 야후 시간봉 값은 조회마다 바뀔 수 있다. [관찰] 그래서 학습에 쓴 원자료를 `raw.json`에 그대로 남긴다. [설계]
- 같은 창(5/10-11/9, 738봉)의 12단계 분포는 50, 29, 61, 107, 119, 155, 105, 79, 25, 3, 3, 2. 지시서 숫자(51, 28, 62, 107, 119, 154, 106, 79, 25, 3, 3, 2)와 7칸이 같고 5칸이 1개씩 다르다. 지시서 숫자의 합은 739로 봉 수 738과 1이 어긋난다. [관찰]
- 9시대 시간봉이 0주인 날이 반년에 28일, 그중 27일이 쉬는 날 바로 다음 거래일이다(나머지 1일은 8/27 목). 최근 60일 안의 14일은 같은 날 30분봉·5분봉에 9시대 거래가 있었다(예: 8/18 시간봉 0주, 5분봉 합 92,707주). 야후 시간봉의 누락이다. [관찰] 빠진 거래량은 일별에는 들어 있어 역산 15시대 봉을 부풀렸다. [관찰] 이 때문에 9시대를 뺐다. 15시대 봉은 '일별 - 시간봉 합'으로 역산했었는데, 시간봉 합이 일별보다 큰 날(3일)이 있고 9시대 누락이 섞여 정확하지 않아 역시 뺐다. 처음에는 9시대 0주인 날 15시대만 결측으로 뒀더니, 월요일 15시대 봉이 하나도 남지 않는 부작용이 있었다. 지금은 하루 5개 봉(10-14시대). [설계, 2026-11-11 의장님 결정]
- 0주 9시대를 빼고 보면 9시대 중앙값은 9천 주대에서 15,880주로, 15시대 중앙값은 약 1만 주에서 5,850주로 바뀐다. 누락이 두 시간대의 '평소'를 거꾸로 왜곡하고 있었다. [관찰]
- HDC 점수가 묻는 것은 "이 요일·시간대에 이 단계가 흔했나"이지 "중앙값의 몇 배인가"가 아니다. 그래서 거래가 거의 없던 봉(1-2단계)이 폭증 봉(11-12단계)과 나란히 상위에 오고, 같은 요일·시간대에 큰 봉이 여러 번 있던 폭증 봉은 순위가 낮다. [관찰] 1단계와 12단계 모두 평소(6단계)에서 5-6단계 떨어져 있어 수준 벡터 유사도가 비슷하게 낮다. [수학]
- 야후 5분봉에는 9시대 거래가 있었다. 시간봉 대신 5분봉(최근 60일)을 시간대별로 합쳐 9-14시대 6개 봉을 만들기로 했다(2026-11-11 의장님 결정). 학습 봉 354개(59일), 요일·시간대 칸마다 11-13개. [설계, 관찰]
- 5분봉 합과 야후 시간봉은 정확히 같은 봉이 354개 중 151개지만, 상대 차이 중앙값은 0.1%, 95% 지점은 19%다. 큰 차이는 야후 시간봉 9시대가 0인 날(14일)이다. [관찰]
- 15시대(15:00-15:30)는 야후 5분봉에 없다. '일별 - 5분봉 합'으로 역산하면 60일 중 8일이 음수였다. 그래서 15시대는 계속 뺀다. [관찰]
- 아래 수치 중 620봉(10-14시대, 시간봉 반년) 기준이라 적힌 것은 5분봉으로 바꾸기 전의 기록이다. 5분봉 60일 기준: 정수 점수와 단순 카운트의 순위 상관 0.90, 이진 점수 0.51, 두 점수끼리 0.63. 이름을 바꿔 다시 만들면 0.78-0.84, 하위 30 중 19개 겹침. 평소의 16배 이상이던 봉 4개의 순위 1, 14, 20, 45위. [관찰]
- 처음에는 이진 프로토타입(다수결 0/1)과의 해밍 유사도만 썼다. 독립 검토에서 다수결이 정보를 많이 잃는다는 지적을 받고 둘을 나란히 계산했다: 단순 카운트(같은 요일·시간대 다른 봉들과의 단계 가까움 합)와의 순위 상관은 정수 점수 0.93, 이진 점수 0.60, 두 점수끼리 0.65(620봉 기준). [관찰] 정수 점수의 기댓값은 그 합에 비례하고, 이진 점수는 비선형 함수다. [수학] 그래서 정수 점수를 본 점수로 쓴다. [설계]
- 정수 점수로는 평소의 16배 이상이던 봉 5개가 모두 하위 30위 안(1, 2, 6, 13, 24위)에 든다. [관찰]
- 벡터 이름 앞에 글자를 붙여 전혀 다른 벡터로 다시 계산하면 순위 상관 0.79-0.86, 하위 30개 중 19-21개만 겹친다. crosstalk는 실행마다 바뀌는 잡음이 아니라 벡터 선택에 따라 고정되는 치우침이다. '이상' 판정 하나하나를 확정된 답으로 읽으면 안 된다. [관찰]
- 요일 ⊕ 시간대 열쇠 25개는 쌍마다 거의 무관하지만 독립이 아니다: (월 ⊕ 10시) ⊕ (월 ⊕ 11시) ⊕ (화 ⊕ 10시) = 화 ⊕ 11시. [수학] 정수 프로토타입 1만 칸 중 18칸은 620개 봉이 모두 같은 값이었다. crosstalk가 구조를 가진다. [관찰]
- 자기 제외는 정수 프로토타입에만 적용된다. 그 봉 자신의 거래량은 중앙값, 단계 경계, 판정 기준 계산에 여전히 들어 있다. [설계]

## ② 더하기: 매물벽 찾기 (`volume/walls.py`)

의장님 질문: "매물이 쏟아질 때의 가격. 그 가격이 되면 매물이 나와 주가가 더 오르지 못한다." 최근 반년 일봉으로 본다(시간대 모델과 같은 기간). 결과는 `walls.json`.

| 단계 | 연산 | 하는 일 |
| --- | --- | --- |
| 거래량 단계 | 일반 계산 | 그날 거래량 ÷ 반년 일별 거래량 중앙값을 12단계로(시간대 모델과 같은 경계). |
| 닿음과 결과 | 일반 계산 | 그날 저가-고가가 걸친 2% 가격칸마다, 종가가 칸 아래면 밀림, 위면 돌파, 안이면 안착. |
| 벡터 | 벡터 생성 | 가격칸 `가격칸:k`, 결과 `결과:밀림` 등은 서로 무관한 벡터. 거래량 단계는 수준 벡터. |
| 묶기 | 묶기 | 닿음 하나 = 가격칸 ⊕ 결과 ⊕ 거래량 단계. |
| 프로토타입 | 더하기 | 최근 20거래일, 60거래일 따로. |
| 묻기 | 묶기, 비교 | 프로토타입 ⊕ 밀림 ⊕ 12단계 → 가격칸마다 점수. 밀린 날이 많고 그때 거래량 단계가 클수록 높다. |

가격칸 k = [1.02^k, 1.02^(k+1))원. 기준이 고정이라 실행마다·종목마다 칸 경계가 같다. 1,200원은 1,199-1,223원 칸. [설계]

### 만들면서 확인된 것
- 2026-10-22부터 11-10까지는 장중 1,192-1,305원까지 가고도 종가가 모두 1,103-1,186원이었다. [관찰]
- 결과는 다섯 가지: 밀림(올라와 닿고 아래로 마감), 하락관통(위에서 뚫고 내려감), 안착, 돌파(아래에서 뚫고 올라감), 지지(내려와 닿고 위에서 마감). 처음에는 종가만 보고 세 가지로 나눠, 내려와 버틴 날까지 '돌파'로 잘못 불렀다. [설계]
- 최근 20거래일(10/15-11/11): 1,153-1,176원 칸 닿음 13 밀림 7, 1,176-1,199원 닿음 11 밀림 7 돌파 0, 1,199-1,223원 닿음 7 밀림 5 돌파 0. 정수 점수 상위 3칸과 카운트 상위 3칸이 같다. 카운트와의 순위 상관은 정수 점수 0.91, 이진 점수 0.80. 60거래일은 0.94, 0.90. [관찰]
- 그 밀린 날의 거래량은 평소(반년 중앙값)의 절반 정도였다(배율 중앙값 0.50-0.56). 이 기간의 벽은 "거래가 쏟아지며 밀림"이 아니라 "거래 없이 그 위로 못 감"에 가깝다. [관찰]
- 이 자료로는 누가 팔았는지 알 수 없다. 매매 주체(기관·외국인·개인) 자료가 없다. [사실]

### 폐기한 첫 시도: 매물대 모델(가격대 ⊕ 거래량 단계)
시간봉 대표 가격을 12개 가격대로 나눠 "가격대 ⊕ 거래량 단계"를 더했다. 질문에 맞지 않아 매물벽 찾기로 바꿨다. 배운 것:
- 거래 한 건에는 사는 쪽과 파는 쪽이 하나씩 있다. 거래량만으로는 매물이 쏟아졌는지(파는 쪽이 몰렸는지) 알 수 없다. '거래 폭증 + 하락 = 매물 출회'는 관례적 해석이다. [사실]
- 처음에는 가격대도 수준 벡터(이웃끼리 닮게)로 만들었다. 그러자 가격대마다 풀어 물은 답이 12칸 모두 6단계로 같았다. [관찰] 두 재료 쌍의 다른 칸들이 서로 무관하게 퍼져 있으면 묶은 벡터끼리의 유사도의 기댓값은 재료 유사도의 곱이라(E[sim(a⊕b, c⊕d)] = sim(a, c) × sim(b, d), b = d면 정확히 sim(a, c)), 서로 다른 사다리 둘을 묶으면 가격대가 다른 봉도 서로 닮아 한 중심으로 뭉친다. [수학] 실측: 가격대 4 ⊕ 6단계와 가격대 7 ⊕ 2단계는 곱으로 예측 0.463, 실측 0.476. 무관한 가격대 벡터로 바꾸면 -0.004. [관찰]
- 서로 다른 벡터 두 개를 60번, 20번 더하면 다수결 결과는 60번 쪽과 똑같다. 적은 쪽은 이진 프로토타입에서 완전히 사라진다. [수학, 테스트로 확인]
- 매물대 점수(봉 벡터와 프로토타입의 유사도)는 그 가격대에 봉이 많을수록 높다. 봉 수와 점수의 순위 상관 0.89. 이 점수는 "그 가격대에서 그 거래량이 드물었나"와 "그 가격대에 머문 적이 드물었나"가 섞여 있다. [관찰] 시간대 모델은 요일·시간대마다 봉 수가 23-27개로 비슷해 이 문제가 작다. [관찰]

## ③ 화면 (`docs/`)

빌드 없는 정적 HTML, CSS, JS. 화면 코드에는 설명 문구가 없고, 모두 추적 기록에서 읽어 온다. 용어 풀이만 `docs/data/glossary.json`에 따로 둔다.

| 부분 | 하는 일 |
| --- | --- |
| 문자판(맨 위 한 줄) | 종목 이름과 코드, 가장 최근 봉의 거래량 점수, 오늘의 새 조합(⑤ 전까지 준비 중) |
| 톱니바퀴(하루치) | 날짜를 고르면 그날의 실제 자료가 ① 받은 거래량 ② 평소(중앙값) ③ 배율과 단계 ④ 재료 벡터 ⑤ 묶기 ⑥ 프로토타입 ⑦ 비교 ⑧ 점수와 판정을 지나는 모습. 벡터는 "앞 4칸 ··· 뒤 4칸" 숫자 줄. 설명은 "왜?" 안에 접는다. 계산은 브라우저에서 `hdc.js`로 다시 하고 파이썬 값과 대조한다. |
| 전체 계산 기록(접힘) | 가장 최근 실행의 단계 전부. 값, 표, 단순 카운트 대조, 숫자 전체, 비트 격자, 그 실행 커밋의 소스 줄 링크. 매물벽은 이것만 보인다. |
| 운행 기록 | 실행마다 시각, 받은 건수, 실패, 추적 기록 링크. |

### 확인된 것
- 브라우저가 다시 계산한 점수가 파이썬 점수와 같았다: 정수 점수와 이진 점수 모두, 가장 최근 날과 가장 드문 봉이 있는 날의 5개 봉 전부에서. [관찰] 같은 이름에서 같은 벡터, 같은 동점깨기를 쓰도록 구현했기 때문이다. [설계]
- 휴대폰 크기(iPhone 13 흉내)에서 가로 넘침 없음, 스크립트 오류 없음. [관찰]
